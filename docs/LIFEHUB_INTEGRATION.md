# Life Hub 연결

## 현재 연결 방식 (P3)

켜켜이는 Life Hub의 OAuth 공개 클라이언트로 연결된다. 비밀 값은 없고 `public/lifehub-client.json`(Client ID Metadata Document)으로 자신을 식별한다. 설정 → **Life Hub 연결** → 소유자 비밀번호 → 켜켜이로 돌아온다 (PKCE S256, `state`·`iss` 검증). 받는 권한은 `kyeokyeoi:inbox` 하나뿐이다.

- **제안 종류**: `memory`(제목·내용·시기 표현·말한 날짜·장소 표현·감정)와 `visit`(장소 표현·방문 날짜). 지역 코드·사진·대화 원문은 받지 않는다. **추억 제안은 방문을 만들지 않는다.**
- **승인**: 추억은 기존 "새 추억" 시트가 미리 채워진 채로 열리고, 지역은 장소 표현으로 검색된 목록에서 직접 고른다. 방문은 지역을 고르고 날짜를 확인한 뒤 기록한다. 이미 방문한 지역이면 기존 기록을 그대로 둔다.
- **영수증**: 저장된 기억·방문의 `source = { service: 'life-hub', originalId: <제안 키> }`가 같은 IndexedDB 트랜잭션으로 저장되고, 이것이 Life Hub로 보내는 영수증이다. 같은 제안으로 기억을 두 번 만들 수 없다. 백업에도 그대로 포함된다.
- **아웃박스**: 영수증과 거절은 Life Hub가 응답할 때까지 재시도한다. 상태가 다르면(409) 재시도를 멈추고 표시만 하며, 켜켜이 기록은 유지한다.
- **Claude 카드에서 승인한 제안 (Life Hub P4 2단계)**: 동기화는 `status=open`(대기 + 카드에서 승인됨)이고 카드에서 고친 내용(`final_candidate`)을 우선한다. 앱을 열 때 `approved`이고 `needs_app_review=false`이며 설정 「Claude에서 승인된 항목 자동 반영」(기본 켜짐, 기기별 `kyeokyeoi.lifehub.auto-apply.v1`)이 켜져 있으면 바로 저장하고 영수증을 보낸다. 단, 시군구는 아래 공유 목록의 표시 이름과 **정확히 같을 때만** 쓴다. 방문은 시군구가 꼭 있어야 하고, 추억은 장소가 없거나 시군구가 정확할 때만 저장한다. 나머지(「켜켜이에서 정할게요」 포함)는 제안 목록에 「Claude에서 승인함」으로 남는다.
- **시군구 목록 공유**: 연결·동기화 때 `PUT /kyeokyeoi/v1/refs/regions`로 `{revision, items: [{id: 코드, label: '경기 고양시 일산서구', group: '경기'}]}`(251개, 공개 지도 데이터뿐)를 올린다. 카드의 시군구 선택지가 된다. `REGIONS_REF_REVISION`이 바뀔 때만 다시 보낸다(`public/regions.json`을 바꾸면 올릴 것).
- 저장 위치(이 브라우저 전용): 토큰 `kyeokyeoi.lifehub.tokens.v1`, 전송 결과·거절·방문 영수증 `kyeokyeoi.lifehub.*.v1`.

# Life Hub 연결 계약 (초안 v1)

이 문서는 Life Hub와의 연결 지점을 정의하는 설계 원칙이다. 현재 구현은 `src/integration/`(OAuth 연결, 제안 수신·영수증, 보드 타일 업로드)에 있고, 서버, Supabase 인증, ChatGPT·Claude API 호출은 이 앱에 없다. 켜켜이는 연결하지 않아도 로컬 저장소만으로 작동한다. 이 앱의 기록 자체는 Hub에 올리지 않는다(올리는 것은 보드용 목록과 공개 시군구 목록뿐이다). Achievement 저장소는 수정하지 않았다.

## 계약과 저장 위치

- `src/integration/contracts.ts`: `ArchiveEnvelope`, `ArchiveLink`, `sourceKey`.
- `src/db/model.ts`: 원본 ID, `SourceReference`, 기억·방문 타입.
- `src/db/index.ts`: 이름이 지정된 로컬 Repository. UI는 이 API를 사용한다. 향후 인증·전송 계층은 이 밖에 추가한다.
- 로컬 `Memory.id`와 `RegionVisit.id`는 생성 후 유지한다. 외부 ID로 원래 ID를 교체하지 않는다.
- 외부 키는 `(service, originalId)` 두 필드를 함께 사용한다. 서비스명/ID에 구분 문자가 있어도 충돌하지 않도록 튜플로 직렬화한다.
- `revision`은 외부 원본 수정 버전이다. `updatedAt`이나 기록한 날짜와 같은 의미가 아니다.
- `certainty`는 `confirmed` 또는 `inferred`. 전송자와 실제 확인 주체를 혼동하지 않는다. 사용자 확인은 별도 `confirmedByUser`에 남긴다.
- 제목·본문·원래 시간 표현·지역 코드·사진 참조는 원본대로 보존한다. 나이·학년 환산 `computedYear`는 검색용 추정 값이다.

## 입력 및 충돌 정책

1. 수신 레이어는 계약 버전, 필수 필드, 사진 소유 관계와 실제 사용자 동의를 검사해야 한다.
2. `idempotencyKey`는 재시도에도 유지한다. 외부 원본 키와 버전을 함께 비교한다. 현재 로컬 백업 가져오기와 외부 수신 API를 혼용하지 않는다.
3. 같은 원본 키·같은 버전·같은 내용은 다시 만들지 않는다. 같은 버전인데 다른 내용이면 충돌이다.
4. 높은 버전은 자동 덮어쓰지 않는다. 로컬 편집과 원본 변경을 사용자에게 비교한 뒤 명시적으로 반영한다. 낮은 버전은 기존 내용을 유지한다.
5. AI가 추정한 시기·지역은 원본 메타데이터에 남길 수 있으나 방문 확인을 생성해서는 안 된다. 사용자 확인 전에는 제안으로만 취급한다.
6. 방문은 사용자의 독립적인 확인이다. 기억의 장소, 위치 추정, 활동 링크가 방문 확인을 대신하지 않는다. `recordedAt`을 실제 `visitedOn`으로 복사하지 않는다.
7. 삭제 전파와 tombstone은 아직 구현하지 않았다. 외부 삭제 때문에 로컬 기억·사진·방문을 자동 삭제하면 안 된다.

## Achievement와 같은 경험 연결

| 상황 | 저장·집계 정책 |
| --- | --- |
| 일상 활동 | Achievement만 원본으로 유지 |
| 사용자가 기억으로 남기기로 선택 | 켜켜이에 기억 생성, `inspired-memory` 관계로 원본 활동 참조 |
| 두 서비스가 같은 경험을 다룸 | `same-experience` 관계와 안정적인 원본 ID로 중복 집계 방지 |
| 지역 방문 확인 | 켜켜이 방문만 변경. 특정 행동 업적 달성으로 해석하지 않음 |
| 방문·기억·활동 관계 | 링크로 연결하고 원문을 반복 복제하지 않음 |

Achievement의 평가 엔진은 그대로 둔다. 미래 집계자는 `(service, originalId)` 또는 사용자가 확인한 `same-experience` 그룹을 한 번만 집계해야 한다. 연결 관계 자체가 행동 수행 증거는 아니다.

## 향후 필요한 구현

실제 Life Hub 스키마·API·인증과 사용자 권한, 원본 키 유일성 인덱스, 수신 검증기, 중복 방지 원장, 충돌 비교 화면, 삭제·철회 정책, 오프라인 전송 큐를 계약 확정 후 구현한다. Supabase RLS·로그인·사진 권한은 서버 계약에 맞춰 별도로 검증한다. 가짜 로그인·동기화 성공 표시나 임의의 외부 endpoint는 두지 않는다.
